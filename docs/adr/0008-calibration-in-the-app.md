# ADR 0008 — Calibration in the app, over kernel runs

**Status**: accepted (M4)

## Context

SPEC §12 planned calibration with the kernel's `GSSK_CalibrateGradient` (Levenberg–Marquardt with
forward sensitivity). Tried on the reservoir example, with observations generated by the model
itself and two rates moved 50 % off, it returned `GSSK_SUCCESS` but stopped at the same point
after 50 and after 500 iterations: rates still far from the truth (runoff 1.19 against 0.80),
misfit only halved. Its observations must also be passed as `GSSK_NodeObservations` structs, so
the caller writes wasm32 field offsets by hand: the ABI fragility the kernel's own header warns
against for results.

## Decision

Calibrate in the app (`src/fit/lm.ts`, `src/fit/calibrate.ts`): least squares over θ = ln k,
residuals scaled per series, Levenberg–Marquardt with a forward-difference Jacobian, where every
residual evaluation is a full run on the pinned kernel. The kernel still does all integration;
the app only chooses the next rates. File the behaviour as kernel request K-6.

Sensitivity follows the same pattern: elasticities by central differences on kernel runs
(`src/fit/sensitivity.ts`), not `GSSK_EnableForwardSensitivity`, so it measures the model exactly
as it runs, solver and method included.

## Consequences

- Recovers known rates to three significant figures in the kernel tests, deterministically.
- Costs (p + 1) runs per iteration for p rates, plus the damped trials. That is fine for the
  model sizes K-4 allows, and progress and Cancel keep it responsive.
- When K-6 is resolved, the kernel's gradient path can be offered as a faster option, checked
  against this one.
